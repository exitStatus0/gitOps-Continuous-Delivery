Section 1: ArgoCD Fundamentals (25 pts)

Question 15 pts
What is ArgoCD?
Answer: B — ArgoCD is specifically designed as a declarative, GitOps-based continuous delivery tool for Kubernetes. It’s not a CI platform, container registry, or monitoring tool, though it integrates with those components.
Question 25 pts
Which architectural pattern does ArgoCD follow for multi-cluster management?
Answer: B — ArgoCD uses a hub-and-spoke architecture where a central control-plane cluster manages deployments to multiple target clusters, providing a single pane of glass.
Question 35 pts
In the context of GitOps, what role does ArgoCD play?
Answer: B — ArgoCD is the automation agent that implements GitOps principles. It continuously pulls the desired state from Git and reconciles it with the live state in Kubernetes clusters.
Question 45 pts
True or False: ArgoCD uses a push-based deployment model where CI/CD pipelines push changes directly to clusters.
Answer: False — ArgoCD uses a pull-based model. It pulls changes from Git repositories rather than having CI/CD pipelines push to clusters. This improves security and follows the GitOps principle of “pulled automatically.”
Question 55 pts
How does ArgoCD handle configuration drift?
Answer: C — When ArgoCD detects drift, it automatically or manually (depending on sync policy) reconciles the live state to match Git. This self-healing capability is a core feature.

Section 2: ArgoCD and GitOps (20 pts)

Question 65 pts
What does “continuous reconciliation” mean in the context of ArgoCD?
Answer: C — Continuous reconciliation means ArgoCD constantly compares the desired state (Git) with the live state (cluster) and automatically corrects any differences.
Question 75 pts
Which GitOps principle does ArgoCD support by using Git as the source of truth?
Answer: B — By using Git as the single source of truth, ArgoCD supports declarative configuration with versioning (Git history) and immutability (Git commits are immutable).
Question 85 pts
True or False: ArgoCD requires write access credentials to the Kubernetes cluster to be stored in the CI/CD pipeline.
Answer: False — Since ArgoCD runs inside the cluster and pulls from Git, the CI/CD pipeline doesn’t need write access to the cluster. CI only needs to update Git. This reduces the attack surface.
Question 95 pts
What happens when ArgoCD detects that the live cluster state differs from the desired state in Git?
Answer: B — ArgoCD’s behavior depends on the sync policy. With auto-sync it immediately reconciles; with manual sync it alerts users but waits for approval. Either way, it can restore the desired state from Git.

Section 3: ArgoCD and Continuous Delivery (20 pts)

Question 105 pts
In a CD workflow with ArgoCD, what is the primary responsibility of ArgoCD?
Answer: C — ArgoCD focuses on the deployment phase — taking built, tested applications and deploying them to Kubernetes. CI handles building and testing; Git handles source code management.
Question 115 pts
How does the CI pipeline typically interact with ArgoCD in a GitOps workflow?
Answer: B — CI updates Kubernetes manifests (usually with new image tags) in a Git repository, and ArgoCD automatically detects and deploys the changes. This separation of concerns is key to GitOps.
Question 125 pts
True or False: ArgoCD handles both the CI (Continuous Integration) and CD (Continuous Delivery) phases of the software delivery pipeline.
Answer: False — ArgoCD focuses on CD only. It doesn’t build code, run tests, or create container images — that’s the job of CI tools like Jenkins, GitLab CI, or GitHub Actions.
Question 135 pts
What is a key benefit of using ArgoCD for the deployment phase of CD?
Answer: C — ArgoCD enables declarative deployments with complete Git audit history and easy rollback via git revert.

Section 4: ArgoCD and Kubernetes (20 pts)

Question 145 pts
How are ArgoCD applications defined in Kubernetes?
Answer: B — ArgoCD uses Kubernetes CRDs to define applications. This makes it Kubernetes-native, so administrators can use familiar tools like kubectl and YAML.
Question 155 pts
Which configuration management tools does ArgoCD support? (Choose the MOST complete answer)
Answer: C — ArgoCD supports plain YAML manifests, Helm charts, Kustomize, Jsonnet, and custom config management plugins. This flexibility lets teams use their preferred tools.
Question 165 pts
True or False: ArgoCD configurations are portable between Kubernetes clusters regardless of the underlying infrastructure.
Answer: True — Since ArgoCD uses Kubernetes-native CRDs and standard manifests, configurations are portable across any cluster — AWS, GCP, Azure, on-premises, or local clusters like kind or minikube.
Question 175 pts
What does the ArgoCD syncPolicy: automated: {} configuration enable?
Answer: B — Setting syncPolicy: automated: {} enables auto-sync, meaning ArgoCD will automatically deploy changes from Git without manual intervention.

Section 5: ArgoCD Features and Best Practices (15 pts)

Question 185 pts
What does the ArgoCD web UI enable users to do?
Answer: B — The ArgoCD UI visualizes Kubernetes resources and their relationships, manages application lifecycles, shows sync and health status, provides log access, and allows manual sync triggers.
Question 195 pts
True or False: In a GitOps workflow with ArgoCD, it is recommended to keep application source code and Kubernetes configuration manifests in the same repository.
Answer: False — Best practice is to separate application source code and Kubernetes manifests into different repositories for better security, separation of concerns, and independent versioning.
Question 205 pts
What is the “App of Apps” pattern in ArgoCD?
Answer: B — The “App of Apps” pattern uses one parent ArgoCD Application that points to a directory containing definitions for multiple child Applications, making it easy to manage entire environments as a single unit.
