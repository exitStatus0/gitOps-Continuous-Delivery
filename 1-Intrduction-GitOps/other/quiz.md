## Раздел 1: Основные принципы GitOps (25 баллов)

### Вопрос 1 (5 баллов)

A) Pulled Automatically  
B) Declarative  
C) Continuously Reconciled  
D) Versioned and Immutable
<details>
<summary>Нажмите, чтобы увидеть ответ</summary>

**Правильный ответ: B** — Declarative

**Объяснение:** Принцип Declarative (Декларативность) является одним из четырех основных принципов GitOps. Он требует, чтобы система, управляемая с помощью GitOps, имела свое желаемое состояние, выраженное декларативно — определяя то, *что* должно существовать, а не то, *как* этого достичь.

</details>

## Раздел 2: Модели Push vs. Pull (20 баллов)

---
### Вопрос 6 (5 баллов)

B) Конвейер CI/CD напрямую применяет манифесты к Kubernetes API  
C) Для развертывания не требуются учетные данные  
D) Система самовосстанавливается автоматически
<details>
<summary>Нажмите, чтобы увидеть ответ</summary>

**Правильный ответ: B** — Конвейер CI/CD напрямую применяет манифесты к Kubernetes API

**Объяснение:** В модели push конвейер CI/CD имеет права записи в кластер и напрямую проталкивает изменения, применяя манифесты к Kubernetes API. Это традиционный подход до появления GitOps.

</details>

### Вопрос 7 (5 баллов)

<details>
<summary>Нажмите, чтобы увидеть ответ</summary>

**Правильный ответ: C** — Оператор GitOps отслеживает Git и затягивает изменения для их применения

**Объяснение:** Модель pull является фундаментальной для GitOps. Оператор GitOps, работающий в кластере, непрерывно отслеживает репозиторий Git и автоматически затягивает изменения, применяя их для поддержания желаемого состояния.

</details>

### Вопрос 8 (5 баллов)

**Объяснение:** Основным преимуществом безопасности модели pull является то, что конвейеру CI/CD не нужны учетные данные с правами записи в кластер. Источник истины исходит из Git, а сервис внутри кластера применяет изменения, следуя принципу наименьших привилегий.

</details>

<details>
<summary>Нажмите, чтобы увидеть ответ</summary>

**Правильный ответ: Неверно**

**Объяснение:** Это неверно. Модель push фактически считается "императивной", потому что она определяет последовательность шагов для достижения конечной цели. Модель pull (GitOps) является декларативной, потому что вы определяете то, что должно существовать, а не то, как этого достичь.

</details>

## Раздел 3: GitOps и Continuous Delivery (20 баллов)

---
### Вопрос 10 (5 баллов)
Как GitOps соотносится с Continuous Delivery?

A) Это конкурирующие практики, которые нельзя использовать вместе  
B) GitOps управляет состоянием среды, в то время как CD автоматизирует поток изменений  
C) GitOps заменил необходимость в Continuous Delivery  
D) Это идентичные практики с разными названиями
<details>
<summary>Нажмите, чтобы увидеть ответ</summary>

**Правильный ответ: B** — GitOps управляет состоянием среды, в то время как CD автоматизирует поток изменений

**Объяснение:** GitOps и CD дополняют друг друга. CD фокусируется на автоматизации конвейера выпуска ПО (сборка, тестирование, доставка), в то время как GitOps обеспечивает механизм развертывания и управления. Они работают вместе для достижения общей цели — более быстрой и качественной доставки программного обеспечения.

</details>

---

<details>
<summary>Нажмите, чтобы увидеть ответ</summary>

**Правильный ответ: Неверно**

**Объяснение:** Это неверно. GitOps и CD — это связанные и взаимодополняющие практики. Они работают вместе для достижения одной и той же цели — доставки программного обеспечения быстрее и с лучшим качеством за счет автоматизации и непрерывной обратной связи.

</details>

<summary>Нажмите, чтобы увидеть ответ</summary>

<summary>Нажмите, чтобы увидеть ответ</summary>

**Правильный ответ: C** — Через Pull Requests, которые позволяют проводить проверку аналогично изменениям кода

</details>
