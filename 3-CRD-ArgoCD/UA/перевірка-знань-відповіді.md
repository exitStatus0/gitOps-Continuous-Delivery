## Розділ 1: Основи Application CRD (25 балів)

### Питання 1 (5 балів)
Що таке ArgoCD Application CRD?

**Правильна відповідь: B** - Kubernetes Custom Resource, що представляє розгорнутий додаток

**Пояснення:** ArgoCD Application є Kubernetes Custom Resource (CR), визначеним Custom Resource Definition (CRD). Він представляє розгорнутий додаток у вашому кластері та містить всю інформацію, необхідну ArgoCD для розгортання та управління цим додатком. Це не Docker образ (A), CLI інструмент (C) або сервіс моніторингу (D).

---

### Питання 2 (5 балів)
Яке поле в Application CRD є обов'язковим і визначає звідки беруться маніфести?

**Правильна відповідь: C** - `spec.source`

**Пояснення:** Поле `spec.source` є обов'язковим і визначає, звідки ArgoCD повинен отримати маніфести (Git-репозиторій, Helm-репозиторій тощо). Хоча `spec.destination` (A) та `spec.project` (D) також є обов'язковими, питання конкретно стосується того, звідки *беруться* маніфести. `spec.syncPolicy` (B) є необов'язковим.

---

### Питання 3 (5 балів)
Так чи Ні: Application CRD може розгортати тільки звичайні YAML маніфести.

**Правильна відповідь: Ні**

**Пояснення:** ArgoCD Applications підтримують кілька інструментів управління конфігурацією, включаючи Helm, Kustomize, Jsonnet, plain YAML/JSON та користувацькі плагіни. Ця гнучкість дозволяє командам використовувати свої улюблені інструменти для визначення ресурсів Kubernetes.

---

### Питання 4 (5 балів)
Як ArgoCD відстежує ресурси, розгорнуті Аплікацією?

**Правильна відповідь: B** - Додаючи labels або annotations до ресурсів

**Пояснення:** ArgoCD додає labels або annotations (залежно від налаштованого методу відстеження) до всіх ресурсів, розгорнутих Аплікацією. Це дозволяє ArgoCD моніторити статус здоров'я, виявляти дрейф, виконувати очищення та показувати взаємозв'язки в UI. Він не використовує базу даних (A), ConfigMaps (C) або постійні запити API (D).

---

### Питання 5 (5 балів)
Який з наступних інструментів НЕ підтримується в ArgoCD Applications?

**Правильна відповідь: C** - Terraform

**Пояснення:** Хоча ArgoCD нативно підтримує Helm (A), Kustomize (B), Jsonnet (D) та plain YAML, він не підтримує Terraform нативно. Однак ви потенційно можете інтегрувати Terraform, використовуючи користувацький Config Management Plugin (CMP), але це не вбудований підтримуваний інструмент.

## Розділ 2: Конфігурація джерела (20 балів)

### Питання 6 (5 балів)
У полі `source`, що визначає `targetRevision`?

**Правильна відповідь: B** - Git гілку, тег або коміт для відстеження

**Пояснення:** Поле `targetRevision` вказує, яку версію джерела використовувати. Для Git-репозиторіїв це може бути назва гілки (наприклад, `main`), тег (наприклад, `v1.0.0`) або конкретний SHA коміту. Для Helm chart репозиторіїв він вказує версію chart. Це не має нічого спільного з версією Kubernetes API (A), версією ArgoCD (C) або версією файлу маніфесту (D).

---

### Питання 7 (5 балів)
Так чи Ні: ArgoCD може автоматично визначити, який інструмент управління конфігурацією використовувати на основі файлів у репозиторії.

**Правильна відповідь: Так**

**Пояснення:** ArgoCD виконує автоматичне виявлення інструменту на основі файлів, знайдених у шляху репозиторію. Наприклад, якщо він знаходить `Chart.yaml`, він використовує Helm; якщо знаходить `kustomization.yaml`, використовує Kustomize; якщо знаходить файли `*.jsonnet`, використовує Jsonnet; інакше обробляє файли як plain YAML.

---

### Питання 8 (5 балів)
Якщо репозиторій містить файл `Chart.yaml`, який інструмент ArgoCD автоматично виявить?

**Правильна відповідь: C** - Helm

**Пояснення:** Наявність файлу `Chart.yaml` є стандартним індикатором Helm chart. ArgoCD автоматично виявить це та використає Helm для рендерингу маніфестів. `kustomization.yaml` вказував би на Kustomize (A), `*.jsonnet` на Jsonnet (D), а окремі файли `*.yaml` оброблялися б як plain YAML (B).

---

### Питання 9 (5 балів)
Яка мета вказівки `valueFiles` у конфігурації джерела Helm?

**Правильна відповідь: B** - Вказати, які файли значень використовувати для рендерингу Helm chart

**Пояснення:** Поле `valueFiles` у конфігурації джерела Helm вказує, які файли значень з репозиторію слід використовувати для перевизначення стандартних значень при рендерингу Helm chart. Це дозволяє мати різні конфігурації для різних середовищ (наприклад, `values-production.yaml`, `values-staging.yaml`).

---

## Розділ 3: Конфігурація призначення (15 балів)

### Питання 10 (5 балів)
Як можна вказати цільовий кластер у полі `destination`?

**Правильна відповідь: C** - Або за назвою кластера, або за URL сервера

**Пояснення:** ArgoCD надає гнучкість у вказівці цільового кластера. Ви можете використовувати або назву кластера (наприклад, `name: 'production'`), або URL сервера (наприклад, `server: 'https://prod-cluster.example.com'`). Обидва методи є дійсними і можуть використовуватися на основі ваших переваг. Namespace також має бути вказаний окремо.

---

### Питання 11 (5 балів)
Який URL сервера слід використовувати для розгортання в тому ж кластері, де працює ArgoCD?

**Правильна відповідь: B** - `https://kubernetes.default.svc`

**Пояснення:** `https://kubernetes.default.svc` є стандартною адресою API сервера Kubernetes всередині кластера. Коли ArgoCD розгорнутий у кластері, і ви хочете розгортати додатки в цей же кластер, використовуйте цей URL. Інші варіанти (A, C, D) не є стандартними адресами всередині кластера.

---

### Питання 12 (5 балів)
Так чи Ні: Ресурси з областю кластера, такі як ClusterRoles, ігнорують namespace, вказаний у полі destination.

**Правильна відповідь: Так**

**Пояснення:** Ресурси з областю кластера (такі як ClusterRoles, ClusterRoleBindings, CustomResourceDefinitions тощо) існують на рівні кластера і не обмежені namespace. Тому поле `namespace` у конфігурації destination ігнорується для цих ресурсів. Тільки ресурси з областю namespace (як Deployments, Services, ConfigMaps) створюються у вказаному namespace.

## Розділ 4: Політики синхронізації та поведінка (25 балів)

### Питання 13 (5 балів)
Що означає "синхронізувати" Аплікацію?

**Правильна відповідь: B** - Узгодити живий стан кластера з бажаним станом з Git

**Пояснення:** Синхронізація Аплікації означає узгодження фактичного стану ресурсів у кластері з бажаним станом, визначеним у Git-репозиторії. ArgoCD отримує маніфести з Git, рендерить їх, порівнює з живим станом кластера та застосовує необхідні зміни для їх відповідності. Це не про резервні копії (A), оновлення ArgoCD (C) або мультикластерну синхронізацію (D).

---

### Питання 14 (5 балів)
Яка конфігурація політики синхронізації вмикає автоматичну синхронізацію при виявленні змін у Git?

**Правильна відповідь: B** - `syncPolicy: automated: {}`

**Пояснення:** Встановлення `syncPolicy.automated` на порожній об'єкт `{}` вмикає автоматичну синхронізацію. ArgoCD буде безперервно опитувати Git-репозиторій та автоматично розгортати зміни без ручного втручання. Немає типів політики синхронізації `manual` (A), `scheduled` (C) або `continuous` (D) в ArgoCD.

---

### Питання 15 (5 балів)
Що робить опція `selfHeal: true`?

**Правильна відповідь: B** - Автоматично повертає ручні зміни, внесені безпосередньо в кластер

**Пояснення:** Опція `selfHeal: true` вмикає автоматичне виправлення дрейфу. Якщо хтось вручну змінює ресурс у кластері (наприклад, `kubectl edit deployment`), ArgoCD виявить дрейф і автоматично поверне зміну для відповідності бажаному стану в Git. Вона не перезапускає pods (A), не виправляє проблеми мережі (C) і не ремонтує Git маніфести (D).

---

### Питання 16 (5 балів)
Так чи Ні: Опція `prune: true` автоматично видалить ресурси з кластера, коли вони видалені з Git.

**Правильна відповідь: Так**

**Пояснення:** Коли встановлено `prune: true` в автоматичній політиці синхронізації, ArgoCD автоматично видалить ресурси з кластера, коли вони видалені з Git-репозиторію. Це забезпечує синхронізацію кластера з Git шляхом видалення ресурсів, які більше не визначені у джерелі.

---

### Питання 17 (5 балів)
Що робить опція синхронізації `CreateNamespace=true`?

**Правильна відповідь: B** - Створює цільовий namespace, якщо він не існує

**Пояснення:** Опція синхронізації `CreateNamespace=true` автоматично створює цільовий namespace у цільовому кластері, якщо він ще не існує. Це корисно для перших розгортань, коли namespace ще не був створений вручну. Вона не створює кластери (A), namespace ArgoCD (C) або резервні namespace (D).

---

## Розділ 5: Життєвий цикл та стани Аплікації (15 балів)

### Питання 18 (5 балів)
Що означає статус "OutOfSync"?

**Правильна відповідь: B** - Живий стан відрізняється від бажаного стану в Git

**Пояснення:** Статус "OutOfSync" вказує, що живий стан ресурсів у кластері не відповідає бажаному стану, визначеному в Git. Це може бути через нещодавні зміни в Git, які ще не синхронізовані, або ручні зміни, внесені безпосередньо в кластер. Це індикатор статусу синхронізації, а не статусу роботи (A), статусу невдачі (C) або статусу схвалення (D).

---

### Питання 19 (5 балів)
Який статус здоров'я вказує, що всі ресурси працюють правильно?

**Правильна відповідь: C** - Healthy

**Пояснення:** "Healthy" — це статус здоров'я, який вказує, що всі ресурси працюють правильно та функціонують як очікується. "Synced" (A) — це статус синхронізації, а не здоров'я. "Progressing" (B) означає, що ресурси створюються/оновлюються. "Active" (D) не є дійсним статусом здоров'я ArgoCD.

---

### Питання 20 (5 балів)
Так чи Ні: Аплікація може бути "Synced", але все ще бути "Degraded" за статусом здоров'я.

**Правильна відповідь: Так**

**Пояснення:** Статус синхронізації та статус здоров'я є незалежними. Аплікація може бути "Synced" (тобто живий стан відповідає бажаному стану в Git), але "Degraded" за здоров'ям (тобто деякі ресурси зазнають невдачі, наприклад, pods у CrashLoopBackOff). Наприклад, якщо Git визначає Deployment з пошкодженим образом контейнера, ArgoCD успішно синхронізує його (статус Synced), але pods зазнають невдачі (статус здоров'я Degraded).

## Напрямки для покращення

На основі того, з якими розділами у вас виникли труднощі:

- **Розділ 1 (Основи)**: Перегляньте основні концепції Application CRD, їхню мету та те, як ArgoCD відстежує ресурси.

- **Розділ 2 (Конфігурація джерела)**: Вивчіть, як Аплікації визначають, що розгортати, включаючи інструменти управління конфігурацією та виявлення інструментів.

- **Розділ 3 (Конфігурація призначення)**: Дізнайтеся про таргетування кластерів, управління namespace та ресурси з областю кластера проти ресурсів з областю namespace.

- **Розділ 4 (Політики синхронізації)**: Зрозумійте поведінку синхронізації, опції автоматизації, самовідновлення, видалення та опції синхронізації.

- **Розділ 5 (Життєвий цикл та стани)**: Опануйте стани Аплікації, статус синхронізації проти статусу здоров'я та що означають різні статуси.

## Наступні кроки

1. **Якщо ви набрали 80+**: Відмінна робота! Дії для виконання:
   - Створюйте складні Аплікації з кількома опціями синхронізації
   - Впровадьте шаблон App of Apps
   - Досліджуйте sync waves та resource hooks
   - Експериментуйте з multi-source Аплікаціями

2. **Якщо ви набрали 60-79**: Гарний прогрес! Дії для виконання:
   - Перегляньте розділи, де ви пропустили питання
   - Створюйте тестові Аплікації з різними конфігураціями
   - Практикуйтеся з автоматичною та ручною синхронізацією
   - Експериментуйте з опціями self-heal та prune

3. **Якщо ви набрали менше 60**: Продовжуйте навчатися! Дії для виконання:
   - Уважно перечитайте матеріали README
   - Почніть з простого розгортання Application
   - Спочатку зрозумійте базову структуру
   - Пройдіть тест знову, коли будете готові

**Рекомендована практика:**
- Створіть Аплікацію для простого додатку (як nginx)
- Увімкніть автоматичну синхронізацію та спостерігайте за поведінкою
- Зробіть ручну зміну розгорнутого ресурсу та спостерігайте за self-heal
- Видаліть ресурс з Git та спостерігайте за видаленням
- Спробуйте різні інструменти конфігурації (Helm, Kustomize, plain YAML)
- Експериментуйте з sync waves для впорядкованого розгортання
