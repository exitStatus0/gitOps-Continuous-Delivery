## Розділ 1: Основи Application CRD (25 балів)

### Питання 1 (5 балів)
Що таке ArgoCD Application CRD?

A) Docker образ для розгортання додатків  
B) Kubernetes Custom Resource, що представляє розгорнутий додаток  
C) Інструмент командного рядка для управління ArgoCD  
D) Сервіс моніторингу для кластерів Kubernetes
<details>
<summary>Натисніть, щоб побачити відповідь</summary>

**Правильна відповідь: B** - Kubernetes Custom Resource, що представляє розгорнутий додаток

**Пояснення:** ArgoCD Application є Kubernetes Custom Resource (CR), визначеним Custom Resource Definition (CRD). Він представляє розгорнутий додаток у вашому кластері та містить всю інформацію, необхідну ArgoCD для розгортання та управління цим додатком. Це не Docker образ (A), CLI інструмент (C) або сервіс моніторингу (D).

</details>

### Питання 2 (5 балів)
Яке поле в Application CRD є обов'язковим і визначає звідки беруться маніфести?

A) `spec.destination`  
B) `spec.syncPolicy`  
C) `spec.source`  
D) `spec.project`
<details>
<summary>Натисніть, щоб побачити відповідь</summary>

**Правильна відповідь: C** - `spec.source`

**Пояснення:** Поле `spec.source` є обов'язковим і визначає, звідки ArgoCD повинен отримати маніфести (Git-репозиторій, Helm-репозиторій тощо). Хоча `spec.destination` (A) та `spec.project` (D) також є обов'язковими, питання конкретно стосується того, звідки *беруться* маніфести. `spec.syncPolicy` (B) є необов'язковим.

</details>

**Пояснення:** Статус синхронізації та статус здоров'я є незалежними. Аплікація може бути "Synced" (тобто живий стан відповідає бажаному стану в Git), але "Degraded" за здоров'ям (тобто деякі ресурси зазнають невдачі, наприклад, pods у CrashLoopBackOff). Наприклад, якщо Git визначає Deployment з пошкодженим образом контейнера, ArgoCD успішно синхронізує його (статус Synced), але pods зазнають невдачі (статус здоров'я Degraded).
