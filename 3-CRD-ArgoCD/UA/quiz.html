Оцінка знань з Application CRD ArgoCD

20 питань · 100 балів · Перевірте своє розуміння Application CRD

Розділ 1: Основи Application CRD (25 балів)

Питання 15 балів
Що таке ArgoCD Application CRD?
Відповідь: B — ArgoCD Application є Kubernetes Custom Resource (CR), визначеним Custom Resource Definition (CRD). Він представляє розгорнутий додаток у вашому кластері та містить всю інформацію, необхідну ArgoCD для розгортання та управління цим додатком. Це не Docker образ (A), CLI інструмент (C) або сервіс моніторингу (D).
Питання 25 балів
Яке поле в Application CRD є обов'язковим і визначає звідки беруться маніфести?
Відповідь: C — Поле spec.source є обов'язковим і визначає, звідки ArgoCD повинен отримати маніфести (Git-репозиторій, Helm-репозиторій тощо). Хоча spec.destination (A) та spec.project (D) також є обов'язковими, питання конкретно стосується того, звідки *беруться* маніфести. spec.syncPolicy (B) є необов'язковим.
Питання 35 балів
Так чи Ні: Application CRD може розгортати тільки звичайні YAML маніфести.
Відповідь: B — ArgoCD Applications підтримують кілька інструментів управління конфігурацією, включаючи Helm, Kustomize, Jsonnet, plain YAML/JSON та користувацькі плагіни. Ця гнучкість дозволяє командам використовувати свої улюблені інструменти для визначення ресурсів Kubernetes.
Питання 45 балів
Як ArgoCD відстежує ресурси, розгорнуті Аплікацією?
Відповідь: B — ArgoCD додає labels або annotations (залежно від налаштованого методу відстеження) до всіх ресурсів, розгорнутих Аплікацією. Це дозволяє ArgoCD моніторити статус здоров'я, виявляти дрейф, виконувати очищення та показувати взаємозв'язки в UI. Він не використовує базу даних (A), ConfigMaps (C) або постійні запити API (D).
Питання 55 балів
Який з наступних інструментів НЕ підтримується в ArgoCD Applications?
Відповідь: C — Хоча ArgoCD нативно підтримує Helm (A), Kustomize (B), Jsonnet (D) та plain YAML, він не підтримує Terraform нативно. Однак ви потенційно можете інтегрувати Terraform, використовуючи користувацький Config Management Plugin (CMP), але це не вбудований підтримуваний інструмент.

Розділ 2: Конфігурація джерела (20 балів)

Питання 65 балів
У полі source, що визначає targetRevision?
Відповідь: B — Поле targetRevision вказує, яку версію джерела використовувати. Для Git-репозиторіїв це може бути назва гілки (наприклад, main), тег (наприклад, v1.0.0) або конкретний SHA коміту. Для Helm chart репозиторіїв він вказує версію chart. Це не має нічого спільного з версією Kubernetes API (A), версією ArgoCD (C) або версією файлу маніфесту (D).
Питання 75 балів
Так чи Ні: ArgoCD може автоматично визначити, який інструмент управління конфігурацією використовувати на основі файлів у репозиторії.
Відповідь: A — ArgoCD виконує автоматичне виявлення інструменту на основі файлів, знайдених у шляху репозиторію. Наприклад, якщо він знаходить Chart.yaml, він використовує Helm; якщо знаходить kustomization.yaml, використовує Kustomize; якщо знаходить файли *.jsonnet, використовує Jsonnet; інакше обробляє файли як plain YAML.
Питання 85 балів
Якщо репозиторій містить файл Chart.yaml, який інструмент ArgoCD автоматично виявить?
Відповідь: C — Наявність файлу Chart.yaml є стандартним індикатором Helm chart. ArgoCD автоматично виявить це та використає Helm для рендерингу маніфестів. kustomization.yaml вказував би на Kustomize (A), *.jsonnet на Jsonnet (D), а окремі файли *.yaml оброблялися б як plain YAML (B).
Питання 95 балів
Яка мета вказівки valueFiles у конфігурації джерела Helm?
Відповідь: B — Поле valueFiles у конфігурації джерела Helm вказує, які файли значень з репозиторію слід використовувати для перевизначення стандартних значень при рендерингу Helm chart. Це дозволяє мати різні конфігурації для різних середовищ (наприклад, values-production.yaml, values-staging.yaml).

Розділ 3: Конфігурація призначення (15 балів)

Питання 105 балів
Як можна вказати цільовий кластер у полі destination?
Відповідь: C — ArgoCD надає гнучкість у вказівці цільового кластера. Ви можете використовувати або назву кластера (наприклад, name: 'production'), або URL сервера (наприклад, server: 'https://prod-cluster.example.com'). Обидва методи є дійсними і можуть використовуватися на основі ваших переваг. Namespace також має бути вказаний окремо.
Питання 115 балів
Який URL сервера слід використовувати для розгортання в тому ж кластері, де працює ArgoCD?
Відповідь: B — https://kubernetes.default.svc є стандартною адресою API сервера Kubernetes всередині кластера. Коли ArgoCD розгорнутий у кластері, і ви хочете розгортати додатки в цей же кластер, використовуйте цей URL. Інші варіанти (A, C, D) не є стандартними адресами всередині кластера.
Питання 125 балів
Так чи Ні: Ресурси з областю кластера, такі як ClusterRoles, ігнорують namespace, вказаний у полі destination.
Відповідь: A — Ресурси з областю кластера (такі як ClusterRoles, ClusterRoleBindings, CustomResourceDefinitions тощо) існують на рівні кластера і не обмежені namespace. Тому поле namespace у конфігурації destination ігнорується для цих ресурсів. Тільки ресурси з областю namespace (як Deployments, Services, ConfigMaps) створюються у вказаному namespace.

Розділ 4: Політики синхронізації та поведінка (25 балів)

Питання 135 балів
Що означає "синхронізувати" Аплікацію?
Відповідь: B — Синхронізація Аплікації означає узгодження фактичного стану ресурсів у кластері з бажаним станом, визначеним у Git-репозиторії. ArgoCD отримує маніфести з Git, рендерить їх, порівнює з живим станом кластера та застосовує необхідні зміни для їх відповідності. Це не про резервні копії (A), оновлення ArgoCD (C) або мультикластерну синхронізацію (D).
Питання 145 балів
Яка конфігурація політики синхронізації вмикає автоматичну синхронізацію при виявленні змін у Git?
Відповідь: B — Встановлення syncPolicy.automated на порожній об'єкт {} вмикає автоматичну синхронізацію. ArgoCD буде безперервно опитувати Git-репозиторій та автоматично розгортати зміни без ручного втручання. Немає типів політики синхронізації manual (A), scheduled (C) або continuous (D) в ArgoCD.
Питання 155 балів
Що робить опція selfHeal: true?
Відповідь: B — Опція selfHeal: true вмикає автоматичне виправлення дрейфу. Якщо хтось вручну змінює ресурс у кластері (наприклад, kubectl edit deployment), ArgoCD виявить дрейф і автоматично поверне зміну для відповідності бажаному стану в Git. Вона не перезапускає pods (A), не виправляє проблеми мережі (C) і не ремонтує Git маніфести (D).
Питання 165 балів
Так чи Ні: Опція prune: true автоматично видалить ресурси з кластера, коли вони видалені з Git.
Відповідь: A — Коли встановлено prune: true в автоматичній політиці синхронізації, ArgoCD автоматично видалить ресурси з кластера, коли вони видалені з Git-репозиторію. Це забезпечує синхронізацію кластера з Git шляхом видалення ресурсів, які більше не визначені у джерелі.
Питання 175 балів
Що робить опція синхронізації CreateNamespace=true?
Відповідь: B — Опція синхронізації CreateNamespace=true автоматично створює цільовий namespace у цільовому кластері, якщо він ще не існує. Це корисно для перших розгортань, коли namespace ще не був створений вручну. Вона не створює кластери (A), namespace ArgoCD (C) або резервні namespace (D).

Розділ 5: Життєвий цикл і стани Application (15 балів)

Питання 185 балів
Що означає статус "OutOfSync"?
Відповідь: B — Статус "OutOfSync" вказує, що живий стан ресурсів у кластері не відповідає бажаному стану, визначеному в Git. Це може бути через нещодавні зміни в Git, які ще не синхронізовані, або ручні зміни, внесені безпосередньо в кластер. Це індикатор статусу синхронізації, а не статусу роботи (A), статусу невдачі (C) або статусу схвалення (D).
Питання 195 балів
Який статус здоров'я вказує, що всі ресурси працюють правильно?
Відповідь: C — "Healthy" — це статус здоров'я, який вказує, що всі ресурси працюють правильно та функціонують як очікується. "Synced" (A) — це статус синхронізації, а не здоров'я. "Progressing" (B) означає, що ресурси створюються/оновлюються. "Active" (D) не є дійсним статусом здоров'я ArgoCD.
Питання 205 балів
Так чи Ні: Аплікація може бути "Synced", але все ще бути "Degraded" за статусом здоров'я.
Відповідь: A — Статус синхронізації та статус здоров'я є незалежними. Аплікація може бути "Synced" (тобто живий стан відповідає бажаному стану в Git), але "Degraded" за здоров'ям (тобто деякі ресурси зазнають невдачі, наприклад, pods у CrashLoopBackOff). Наприклад, якщо Git визначає Deployment з пошкодженим образом контейнера, ArgoCD успішно синхронізує його (статус Synced), але pods зазнають невдачі (статус здоров'я Degraded).
