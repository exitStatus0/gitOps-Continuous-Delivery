Проверка знаний ArgoCD Application CRD

20 вопросов · 100 баллов · Проверьте свое понимание Application CRD

Раздел 1: Основы Application CRD (25 баллов)

Вопрос 15 баллов
Что такое ArgoCD Application CRD?
Ответ: B — ArgoCD Application — это Kubernetes Custom Resource (CR), определенный через Custom Resource Definition (CRD). Он представляет собой развернутое приложение в вашем кластере и содержит всю информацию, необходимую ArgoCD для развертывания этого приложения и управления им. Это не Docker-образ (A), не CLI-инструмент (C) и не сервис мониторинга (D).
Вопрос 25 баллов
Какое поле в Application CRD является обязательным и определяет, откуда берутся манифесты?
Ответ: C — Поле spec.source является обязательным и определяет, откуда ArgoCD должен брать манифесты (Git-репозиторий, Helm-репозиторий и т. д.). Хотя spec.destination (A) и spec.project (D) также обязательны, в вопросе конкретно спрашивается об источнике манифестов. Поле spec.syncPolicy (B) является необязательным.
Вопрос 35 баллов
Верно или Неверно: Application CRD может развертывать только обычные YAML-манифесты.
Ответ: B — ArgoCD Applications поддерживают несколько инструментов управления конфигурациями, включая Helm, Kustomize, Jsonnet, обычный YAML/JSON и пользовательские плагины. Эта гибкость позволяет командам использовать предпочтительные инструменты для определения ресурсов Kubernetes.
Вопрос 45 баллов
Как ArgoCD отслеживает ресурсы, развернутые с помощью Application?
Ответ: B — ArgoCD добавляет метки или аннотации (в зависимости от настроенного метода отслеживания) ко всем ресурсам, развернутым через Application. Это позволяет ArgoCD отслеживать статус здоровья, обнаруживать отклонения (drift), выполнять очистку и отображать связи в интерфейсе. Он не использует базу данных (A), ConfigMaps (C) или постоянные запросы к API (D).
Вопрос 55 баллов
Какой из перечисленных инструментов НЕ является встроенно поддерживаемым инструментом управления конфигурациями в ArgoCD Applications?
Ответ: C — Хотя ArgoCD нативно поддерживает Helm (A), Kustomize (B), Jsonnet (D) и обычный YAML, он не поддерживает Terraform нативно. Однако вы потенциально можете интегрировать Terraform, используя кастомный Config Management Plugin (CMP), но он не является встроенным инструментом.

Раздел 2: Конфигурация источника (20 баллов)

Вопрос 65 баллов
Что определяет поле targetRevision в поле source?
Ответ: B — Поле targetRevision указывает, какую версию источника использовать. Для Git-репозиториев это может быть имя ветки (например, main), тег (например, v1.0.0) или конкретный SHA коммита. Для репозиториев Helm-чартов оно указывает версию чарта. Это не имеет отношения к версии Kubernetes API (A), версии ArgoCD (C) или версии файла манифеста (D).
Вопрос 75 баллов
Верно или Неверно: ArgoCD может автоматически определять, какой инструмент управления конфигурациями использовать, на основе файлов в репозитории.
Ответ: A — ArgoCD выполняет автоматическое обнаружение инструмента на основе файлов, найденных в пути репозитория. Например, если он находит Chart.yaml, используется Helm; если находит kustomization.yaml — Kustomize; если находит файлы *.jsonnet — Jsonnet; в противном случае файлы обрабатываются как обычный YAML.
Вопрос 85 баллов
Если репозиторий содержит файл Chart.yaml, какой инструмент ArgoCD обнаружит автоматически?
Ответ: C — Наличие файла Chart.yaml является стандартным признаком Helm-чарта. ArgoCD автоматически обнаружит это и использует Helm для рендеринга манифестов. kustomization.yaml указывал бы на Kustomize (A), *.jsonnet — на Jsonnet (D), а отдельные *.yaml файлы обрабатывались бы как обычный YAML (B).
Вопрос 95 баллов
Какова цель указания valueFiles в конфигурации источника Helm?
Ответ: B — Поле valueFiles в конфигурации источника Helm определяет, какие файлы значений из репозитория должны использоваться для переопределения значений по умолчанию при рендеринге Helm-чарта. Это позволяет использовать разные конфигурации для разных сред (например, values-production.yaml, values-staging.yaml).

Раздел 3: Конфигурация назначения (15 баллов)

Вопрос 105 баллов
Как можно указать целевой кластер в поле destination?
Ответ: C — ArgoCD обеспечивает гибкость при указании целевого кластера. Вы можете использовать либо имя кластера (например, name: 'production'), либо URL-адрес сервера (например, server: 'https://prod-cluster.example.com'). Оба метода валидны. Пространство имен должно быть указано отдельно.
Вопрос 115 баллов
Какой URL сервера следует использовать для развертывания в тот же кластер, где запущен ArgoCD?
Ответ: B — https://kubernetes.default.svc — это стандартный адрес API-сервера Kubernetes внутри кластера. Если ArgoCD развернут в кластере и вы хотите развернуть приложения в этот же кластер, используйте этот URL. Другие варианты (A, C, D) не являются стандартными внутренними адресами.
Вопрос 125 баллов
Верно или Неверно: Ресурсы уровня кластера (cluster-scoped), такие как ClusterRoles, игнорируют пространство имен, указанное в поле destination.
Ответ: A — Ресурсы уровня кластера (такие как ClusterRoles, ClusterRoleBindings, CustomResourceDefinitions и т. д.) существуют на уровне всего кластера и не привязаны к пространству имен. Поэтому поле namespace в конфигурации назначения игнорируется для этих ресурсов. В указанном пространстве имен создаются только ресурсы уровня пространства имен (например, Deployments, Services, ConfigMaps).

Раздел 4: Политики и поведение синхронизации (25 баллов)

Вопрос 135 баллов
Что означает "синхронизировать" (sync) Application?
Ответ: B — Синхронизация Application означает приведение фактического состояния ресурсов в кластере в соответствие с желаемым состоянием, определенным в репозитории Git. ArgoCD извлекает манифесты из Git, рендерит их, сравнивает с текущим состоянием кластера и применяет необходимые изменения. Это не связано с бэкапами (A), обновлением ArgoCD (C) или синхронизацией кластеров (D).
Вопрос 145 баллов
Какая конфигурация политики синхронизации включает автоматическую синхронизацию при обнаружении изменений в Git?
Ответ: B — Установка syncPolicy.automated в виде пустого объекта {} включает автоматическую синхронизацию. ArgoCD будет постоянно опрашивать Git-репозиторий и автоматически развертывать изменения без ручного вмешательства. В ArgoCD нет типов политик manual (A), scheduled (C) или continuous (D).
Вопрос 155 баллов
Что делает опция selfHeal: true?
Ответ: B — Опция selfHeal: true включает автоматическое исправление отклонений (drift). Если кто-то вручную изменит ресурс в кластере (например, через kubectl edit deployment), ArgoCD обнаружит это отклонение и автоматически вернет ресурс в состояние, описанное в Git. Она не перезапускает поды (A), не чинит сеть (C) и не правит манифесты в Git (D).
Вопрос 165 баллов
Верно или Неверно: Опция prune: true будет автоматически удалять ресурсы из кластера, когда они удаляются из Git.
Ответ: A — Если в автоматической политике синхронизации установлено prune: true, ArgoCD будет автоматически удалять ресурсы из кластера, если они были удалены из репозитория Git. Это гарантирует, что в кластере не останется ресурсов, которые больше не определены в источнике.
Вопрос 175 баллов
Что делает опция синхронизации CreateNamespace=true?
Ответ: B — Опция CreateNamespace=true автоматически создает целевое пространство имен в кластере назначения, если оно еще не существует. Это полезно при первичных развертываниях. Она не создает кластеры (A), пространства имен для ArgoCD (C) или бэкап-пространства имен (D).

Раздел 5: Жизненный цикл и состояния Application (15 баллов)

Вопрос 185 баллов
Что означает статус "OutOfSync"?
Ответ: B — Статус "OutOfSync" указывает на то, что фактическое состояние ресурсов в кластере не совпадает с желаемым состоянием, описанным в Git. Это может быть вызвано недавними изменениями в Git, которые еще не были синхронизированы, или ручными изменениями в кластере. Это индикатор синхронизации, а не статуса работы (A), ошибки (C) или ожидания подтверждения (D).
Вопрос 195 баллов
Какой статус здоровья (health status) указывает на то, что все ресурсы работают правильно?
Ответ: C — "Healthy" — это статус здоровья, указывающий на то, что все ресурсы запущены и функционируют должным образом. "Synced" (A) — это статус синхронизации, а не здоровья. "Progressing" (B) означает, что ресурсы находятся в процессе создания или обновления. "Active" (D) не является валидным статусом здоровья в ArgoCD.
Вопрос 205 баллов
Верно или Неверно: Application может иметь статус "Synced", но при этом иметь статус здоровья "Degraded".
Ответ: A — Статус синхронизации и статус здоровья независимы. Application может иметь статус "Synced" (это значит, что текущее состояние в кластере соответствует описанию в Git), но при этом статус здоровья может быть "Degraded" (это значит, что ресурсы работают со сбоями, например, поды находятся в CrashLoopBackOff). Например, если в Git определен Deployment с нерабочим образом контейнера, ArgoCD успешно синхронизирует его (статус Synced), но поды не запустятся (статус Degraded).
